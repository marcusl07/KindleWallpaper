Leaf Public Beta Refactor Plan

Planning artifact for the current app repository. Source review: launch-technical-review.html.

Goal

Prepare Leaf for a public macOS validation beta while preserving current user-facing behavior. The refactor should make the app easier for future LLM agents and maintainers to change safely: smaller files, clearer ownership, fewer historical paths, one reliable verification entrypoint, and no shipping helper architecture.

This is not an App Store launch plan. It is a public beta plan for posting the app around, learning whether people use it, and avoiding premature paid distribution work.

Decisions

PlatformPublic macOS app beta. Not iOS.
Product nameThe app is named Leaf moving forward. User-facing copy, docs, release material, and newly touched source names should stop using the old brand.
DistributionDirect/GitHub beta distribution. App Store, notarization, and paid signing are deferred until demand is proven.
Product promiseSet-and-forget menu bar utility. Leaf must be running to rotate or restore wallpaper; launch at login starts the main app automatically.
No helperDelete DisplayHelper from shipping source and build graph. Do not archive helper source in the repo; git history is enough.
BehaviorPreserve current user-facing functionality during structural refactors, except for removing helper-only paths.
StorageLocal-only SQLite/GRDB. No accounts, sync, or cloud model in the beta plan.
Core boundaryNo separate package/module yet. Keep one app target and organize by folders/files first.
UIKeep the current UI direction. Focus on internals, reliability, privacy clarity, and beta readiness.

Execution Principles

  • Make behavior-preserving moves before behavior changes.
  • Commit and push each verified phase as a rollback point.
  • Stage only files touched for the current phase; ignore unrelated local, build, trace, and Xcode user-state changes.
  • Prefer boring, feature-named files over clever abstractions.
  • Keep DatabaseManager as a facade during the first database split to reduce blast radius.
  • Use responsibility boundaries over strict line-count targets, but large files need a strong reason to stay large.
  • Do not impose a final folder taxonomy before the splits. Prefer clear file names and local placement first; after the major splits, run a dedicated organization pass around boundaries that proved real.

Phased Plan

Phase 0

Baseline, Inventory, and Safety Net

Intent: establish the current behavior and a canonical verification path before moving architecture.

  • Audit the best existing scripts/verify_t*.sh scripts and identify which represent durable product behavior.
  • Add a real Swift/Xcode test target in project.yml.
  • Create scripts/test.sh as the one blessed local verification command.
  • Keep only a small smoke-script layer for macOS integration behavior that cannot run in ordinary tests.
  • Regenerate the Xcode project after project.yml changes.

Verification: generated project opens/builds, the new test target runs, and scripts/test.sh completes.

Commit boundary: test target plus canonical test wrapper only.

Phase 1

Delete the Non-Shipping Helper Architecture

Intent: make the codebase match the beta promise: one main menu bar app, no helper.

  • Remove DisplayHelper target, embedding, references, and generated project wiring.
  • Delete DisplayHelper/ source files and helper-only login service code.
  • Remove startup unregister/shelving code that only exists because the helper half-exists.
  • Collapse storage/defaults policy that was only needed for helper sharing.
  • Update text-files/background-login-helper-spec.txt or replace it with a current product decision: main app only.

Verification: app builds without DisplayHelper, no embedded login item exists in the product, launch-at-login still controls the main app, and wallpaper behavior remains unchanged while the app is running.

Commit boundary: helper deletion and docs/spec truth update.

Phase 2

Split the Settings and Library UI

Intent: reduce the largest UI file into LLM-friendly feature files without changing visible UI behavior.

  • Split App/SettingsView.swift into feature files such as SettingsView, QuotesListView, QuotesListViewModel, QuotesNativeTableView, QuoteDetailView, QuoteEditView, BooksListView, and BackgroundsListView.
  • Move test probes out of production view files where the new test target can cover behavior directly.
  • Keep the current UI layout and interactions unless a tiny adjustment is required by the split.
  • Preserve quote import, browse, search, edit, delete, selection, paging, and filter behavior.

Verification: tests pass; manual smoke covers opening settings, importing highlights, browsing/searching quotes, editing/deleting, managing books/backgrounds, and generating wallpaper from the library.

Commit boundary: UI file split with no intentional behavior changes.

Phase 3

Split Database Internals Behind the Facade

Intent: shrink Database.swift while keeping DatabaseManager as the app-facing facade.

  • Move schema and migrations into DatabaseSchema and DatabaseMigrations.
  • Move quote paging/search/filter behavior into QuoteRepository.
  • Move import behavior into ImportRepository.
  • Move book/background/delete/tombstone behavior into focused repositories where appropriate.
  • Add regression tests for punctuation-heavy search strings, empty search, long search, import dedupe, deletion, and migration basics.

Verification: tests pass; existing database files migrate/open; quote library behavior and import behavior match the baseline.

Commit boundary: database split preserving the facade and behavior.

Phase 4

Split App State and App Lifecycle Ownership

Intent: make AppState observable UI state, not the owner of every service and lifecycle decision.

  • Extract wallpaper rotation/restoration into WallpaperRotationService and display-specific code into a main-app-only display subsystem.
  • Extract library mutations into LibraryService if the database facade still leaves too much UI-facing orchestration in AppState.
  • Keep launch-at-login as a main-app service only.
  • Split the current app entry file into app entry, app delegate, status item controller, settings window coordinator, and lifecycle test support. Rename source files away from the old brand when doing so.

Verification: launch, menu bar actions, settings window behavior, schedule modes, manual rotation, launch-at-login toggling, and wallpaper restoration smoke tests pass.

Commit boundary: app state/lifecycle split with behavior preserved.

Phase 5

Replace User-Facing Fatal Paths

Intent: after boundaries are clearer, change failure behavior where public beta users would otherwise see crashes.

  • Replace launch/user-facing fatalError database paths with thrown errors.
  • Surface recoverable import, migration, locked database, and file access failures in the UI.
  • Keep truly impossible programmer errors narrow and documented.
  • Add tests for representative failure cases.

Verification: tests pass; simulated bad import/database/file states show user-visible errors instead of crashing where recovery is possible.

Commit boundary: error handling behavior changes.

Phase 6

Beta Readiness and Documentation

Intent: make the validation release understandable to early users without adding App Store infrastructure.

  • Add a GitHub README beta section with install steps, unsigned-app expectations if applicable, manual update instructions, and known limitations.
  • Add clear local-data/privacy language: highlights stay local, no account, no cloud sync, no analytics unless explicitly added later.
  • Fix repo hygiene: generated build products, trace bundles, .DS_Store, and Xcode user state should not be tracked.
  • Run a final manual beta acceptance pass on a fresh-ish local install state.

Verification: clean build, tests, smoke wrapper, README review, fresh install/import/generate/schedule/launch-at-login pass.

Commit boundary: beta docs and hygiene only.

Risk Register

Risk Why it matters Control
Helper deletion regresses launch behavior The repo has historical helper/main-app overlap. Verify launch-at-login controls the main app only, and inspect the built product for no embedded login item.
UI split changes quote library behavior SettingsView.swift currently mixes view, table bridge, state, and probes. Move in narrow slices and run import/search/edit/delete/manual generation smoke checks after each slice.
Database split masks behavior changes Persistence owns schema, import, search, paging, and deletion. Keep DatabaseManager as facade first; add behavior tests before changing call sites.
Error handling becomes a mixed refactor Changing crash behavior while moving files makes regressions hard to isolate. Do structural split first, then convert user-facing failures to thrown errors in a separate phase.
Beta packaging distracts from validation Signing, notarization, auto-update, and App Store work can consume time before demand is proven. Keep first beta manual and direct. Document friction instead of solving all distribution problems now.

Beta Acceptance Checklist

  • Fresh build succeeds from regenerated project.
  • Canonical scripts/test.sh passes.
  • Real test target passes.
  • No DisplayHelper target, source, product, or embedded login item remains.
  • Main app launches normally as menu bar app.
  • Launch-at-login can be enabled and disabled for the main app.
  • Manual wallpaper generation works.
  • Scheduled wallpaper rotation works.
  • On-app-launch rotation behavior is preserved.
  • Wallpaper restore works while the app is running.
  • Quitting behavior is documented: no hidden helper continues work.
  • Kindle highlight import works.
  • Quote browse/search/filter/edit/delete behavior works.
  • Books/backgrounds management still works.
  • Recoverable import/database/file failures show user-visible errors.
  • README explains install, manual updates, local-data privacy, and beta limitations.
  • Generated artifacts and local Xcode state are ignored or left uncommitted.

Not Now

  • No App Store submission work.
  • No auto-updater.
  • No helper resurrection.
  • No iOS app work.
  • No account, sync, cloud, or analytics system.
  • No major visual redesign.
  • No separate Swift package/module until the app-target folders are clean and stable.

Recommended First Commit

Start with Phase 0. The first useful commit should add the test target and scripts/test.sh without touching helper deletion or UI/database refactors. That gives every later phase a repeatable safety check and keeps the first rollback point obvious.
